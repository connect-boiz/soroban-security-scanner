# Coverage-Guided Fuzzing for Soroban Contracts

This document describes the coverage-guided fuzzing infrastructure in `src/coverage_guided_fuzzer/`.

---

## Overview

The fuzzer uses AFL/libFuzzer-style coverage guidance to find bugs in Soroban WASM smart contracts.
Unlike black-box fuzzing (which mutates bytes blindly), coverage-guided fuzzing instruments the
contract binary to track which code paths each input exercises, then prioritises mutations that
explore **new** paths. This routinely finds 10–100× more bugs in the same time budget.

---

## Phase 1 — WASM Instrumentation (`wasm_instrumenter.rs`)

Each basic block entry gets a 4-instruction counter sequence:

```wasm
global.get $__prev_block
i32.const  <BLOCK_ID>
i32.xor
;; → edge_id = prev XOR cur
global.set $__prev_block

global.get $__coverage_counter
i32.const 1
i32.add
global.set $__coverage_counter
```

The `__coverage_counter` global is exported and backed by a **shared memory page** visible to
the fuzzer host so coverage data is read without re-executing the function.

**Overhead target**: < 20% of the contract's original CPU budget (4 new instructions per block,
typical Soroban blocks have ~20 instructions → ~5% overhead at worst).

## Phase 2 — Coverage Map & Corpus (`coverage_map.rs`, `corpus.rs`)

- **Bitmap**: 65 536 entries (64 KB), one per edge slot.  
  `edge_slot = (prev_block_id XOR cur_block_id) % 65536`
- An input is **interesting** if `new_edges(exec) ≠ ∅` — it sets at least one zero bit.
- `Corpus` stores interesting inputs as `CorpusEntry { bytes, execution_time, new_edges, performance_score }`.
- **Performance score** (AFL heuristic):  
  `score = new_edges² / (input_len × exec_ms)`  
  Smaller, faster inputs with more new edges are selected more often for mutation.

## Phase 3 — Structured Input Generation (`input_gen.rs`)

Produces valid Soroban function arguments for all supported types:

| Type | Strategy |
|------|----------|
| `Address` | G… prefix, 56-char Stellar base32 |
| `Symbol` | printable ASCII, ≤ 32 chars |
| `i128` | 30% edge-cases (0, ±1, MIN, MAX, powers-of-2), 40% small exponential, 30% uniform |
| `u64` | similar distribution |
| `Vec<T>` | length in [0, 50], elements generated recursively |
| `Map<K,V>` | up to 20 key-value pairs |
| `Struct` | each field generated by its declared type |
| `Bytes` / `BytesN` | random bytes |

**Ratio**: 90% well-typed, 10% intentionally malformed (`InvalidBytes`) to test deserialization robustness.

## Phase 4 — Mutation Strategies (`mutation.rs`)

| Strategy | Description |
|----------|-------------|
| `bit_flip_N` | Flip N consecutive bits at a random position (N ∈ {1,2,4,8,16,32}) |
| `byte_flip` | XOR a random byte with 0xFF |
| `byte_zero` / `byte_max` | Set a byte to 0x00 / 0xFF |
| `arith_add` / `arith_sub` | Add/subtract ±1..35 from a byte |
| `interesting_val` | Overwrite 8 bytes with a known-dangerous i64 (0, ±1, INT_MAX, …) |
| `splice` | Prefix from current entry + suffix from a random donor corpus entry |
| `struct_splice` | Swap one JSON-level argument between two corpus entries |
| `havoc` | Apply 2–128 random sub-mutations in sequence |

The scheduler selects strategies proportional to their **historical yield** (how many
interesting inputs they produced).

## Phase 5 — Crash Triage (`crash_triage.rs`)

1. **Capture**: error text + input bytes from the VM host.
2. **Normalise**: strip pointer addresses (`0xADDR`), line numbers (`:LINE`), long hex hashes (`HASH`), collapse whitespace.
3. **Fingerprint**: `DefaultHasher` over the normalised string → 16-hex-char ID.
4. **Deduplicate**: only the first crash per fingerprint is reported.
5. **Minimise** (delta-debugging / ddmin):
   - Phase 1 — binary chunking: try removing halves, quarters, … (O(log n) steps).
   - Phase 2 — byte-by-byte scan: remove individual bytes while crash still reproduces.
   - Budget: 256 iterations maximum.

---

## Phase 6 — Persistent Mode (`persistent_vm.rs`)

Instead of fork+exec (~50 ms/input), the fuzzer keeps a single VM instance:

```
deploy → take_snapshot()
  loop:
    execute_raw(input)   → ~1 ms
    restore(snapshot)    → ~1 ms
```

`VmSnapshot` captures:
- Contract storage (key-value pairs)
- WASM globals (index → bytes)
- Linear memory pages
- Original WASM binary (for data-segment re-init)

`VmBackend` is a trait — the production implementation wraps `soroban-env-host`; tests use `StubVmBackend`.

Expected throughput: **1 000+ executions/second** vs ~20/s for fork+exec.

```json
  "current_stage": "havoc",
  "coverage_bitmap_b64": "AAAB…"
}
```

### WebSocket

`ws /api/v1/fuzzer/ws` — the server pushes the same JSON object every second.

### Heatmap

`coverage_bitmap_b64` is a base64-encoded 65 536-byte array. Each byte is 1 if the corresponding
edge has been hit. The frontend renders this as a 256×256 heatmap.

## Phase 8 — CI Integration (`ci_integration.rs`)

```bash
cargo run --bin soroban-scanner -- fuzz \
  --timeout 3600 \
  --corpus-dir ./fuzz-corpus \
  --wasm target/wasm32-unknown-unknown/release/my_contract.wasm
```

Exit codes:
- `0` — no crashes found
- `1` — one or more unique crashes found
- `2` — configuration / setup error

### GitHub Actions caching

```yaml
- name: Restore fuzzing corpus
  uses: actions/cache@v4
  with:
    path: ./fuzz-corpus
    key: fuzz-corpus-${{ hashFiles('target/**/*.wasm') }}
    restore-keys: fuzz-corpus-

- name: Run fuzzer
  run: |
    cargo run --bin soroban-scanner -- fuzz \
      --timeout 3600 \
      --corpus-dir ./fuzz-corpus \
      --wasm target/wasm32-unknown-unknown/release/contract.wasm

- name: Save updated corpus
  if: always()
  uses: actions/cache/save@v4
  with:
    path: ./fuzz-corpus
    key: fuzz-corpus-${{ hashFiles('target/**/*.wasm') }}-${{ github.run_id }}
```

The corpus accumulates across CI runs; each build starts from the previous run's coverage frontier.

## Phase 9 — Differential Fuzzing Integration (`orchestrator.rs`)

Inputs that produce **different behaviour across SDK versions** are treated as interesting even
if they don't increase coverage:

```
for each mutated input:
    run on SDK v25.3.0  →  outcome_a
    run on SDK v25.2.0  →  outcome_b
    if discrepancy(outcome_a, outcome_b):
        corpus.add(input)   ← interesting regardless of coverage
```

Discrepancies checked:
- Return value differs
- Gas consumption differs by > 10%
- One version panics, the other succeeds
- State changes differ

This combines **coverage-guided exploration** (finds deep paths) with **differential comparison**
(finds version-specific bugs at those paths).
